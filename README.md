# Прототип анализа фонограмм на признаки синтезированной речи

Демо-каркас: загрузка фонограммы → спектрограмма → скользящая оценка вероятности синтеза →
классические проверки → отчёт DOCX.

## Запуск

```bash
sudo apt install python3-venv python3-dev libxcb-cursor0 ffmpeg
./run.sh
```

`run.sh` сам создаёт `.venv`, ставит зависимости и запускает приложение.
Зависимости переустанавливаются только когда меняется `requirements.txt` —
скрипт сравнивает его хеш с сохранённым в `.venv/.requirements.sha`.

Системные пакеты ставятся один раз: `libxcb-cursor0` нужен PySide6 на Ubuntu
24.04 (без него Qt не грузит плагин xcb), `ffmpeg` — для форматов и метаданных.
Без системного ffmpeg файлы всё равно откроются через `imageio-ffmpeg`, но в
отчёте не будет строки с кодеком: ffprobe в этом пакете нет.

Поддерживаемые форматы: WAV, FLAC, AIFF, OGG, MP3 читаются через libsndfile;
M4A/AAC, WMA, AMR, Opus — через ffmpeg.

## Важно про режим ЗАГЛУШКИ

Если рядом с `app.py` нет файла `model.onnx`, программа работает на функции
`baseline_score` — это **не детектор**, а две простые спектральные характеристики,
нужные только чтобы интерфейс не был пустым. В заголовке окна и в отчёте это
написано явно. **На защите нельзя выдавать её результаты за детектирование.**

## Детекторы

Все детекторы реализуют один интерфейс `Detector.scores(x, sr, path) -> (times, probs)`
и выбираются в выпадающем списке рядом с кнопкой «Анализ»:

| Пункт списка | Где считает | Что рисует |
|---|---|---|
| ЗАГЛУШКА (локально) | в приложении | кривая, не детектирование |
| ONNX локально | в приложении, при наличии `model.onnx` | кривая |
| SRW: PyTorch — поток | websocket `/audio/stream` | кривая по всему файлу |
| SRW: PyAra — поток | websocket `/audio/stream` | кривая, ступенчатая |
| SRW: PyTorch — файл целиком | очередь `/audio/detect` | ровная линия по одной оценке |
| SRW: PyAra — файл целиком | очередь `/audio/detect` | ровная линия по одной оценке |

Модель для очереди выбирается прямо в запросе — поле `model` формы, значения
`pytorch` и `pyara`. Воркер держит обе и создаёт нужную при первом обращении,
`MODEL_TYPE` остался значением по умолчанию.

Модель для потока выбирается query-параметром `?model=`, шлюз сообщает её воркеру
управляющим сообщением `INIT`.

PyAra в потоке работает через обходной путь: библиотека принимает только файл,
поэтому `process_stream` сохраняет накопленный буфер во временный wav. Это заметно
медленнее PyTorch, а оценка приходит как 0 или 1, так что кривая получается
ступенчатой — сглаживает её только EMA внутри воркера.

Настройки детектора вводятся в интерфейсе: под панелью кнопок появляется строка
полей, своя для каждого режима.

| Режим | Поля |
|---|---|
| локальные детекторы | окно и шаг анализа, с |
| поток | размер чанка, ожидание тишины, общий таймаут, с |
| файл целиком | интервал опроса, таймаут, пауза после 429, с |

Порог общий для всех и вынесен отдельно — при его изменении график
перерисовывается сразу, без повторного анализа. Значения из полей попадают
в журнал и в отчёт, так что результат воспроизводим.

Новый детектор добавляется одним классом в `detectors.py`: описываете `fields`,
и поля ввода строятся сами. Значения из `config.py` остаются значениями
по умолчанию.

## Подключение настоящей модели

1. Взять предобученный анти-спуфинг: AASIST или RawNet2 (обучены на ASVspoof2019 LA),
   либо wav2vec2-модель детекции с Hugging Face.
2. Экспортировать в ONNX (`torch.onnx.export`), положить как `model.onnx`.
3. Проверить, что вход совпадает: в `analysis.onnx_score` подаётся сырой сигнал
   формы `(1, N)` float32. Если модель ждёт мел-спектрограмму — поправить эту
   функцию, остальное менять не нужно.
4. Проверить лицензию весов: часть моделей идёт под non-commercial.

## Файлы

- `config.py` — все настройки: порог, окно, адрес и учётка сервиса
- `detectors.py` — детекторы с общим интерфейсом (заглушка, ONNX, SRW)
- `analysis.py` — ядро: загрузка, скользящие вероятности, классические проверки
- `report.py` — генерация DOCX по всему сеансу: сводка по моделям, общий график, журнал
- `app.py` — интерфейс
- `batch.py` — пакетная обработка папки, выгрузка сводной таблицы
- `player.py` — воспроизведение через QAudioSink
- `service.py` — клиент к бэкенду SRW (логин, отправка, опрос результата)
- `run.sh` — запуск: окружение, зависимости, приложение
- `.gitignore` — окружение, отчёты, модель и тестовые фонограммы в репозиторий не
  попадают; график отчёта строится в памяти и на диск не пишется

## Работа с сервисом SRW

Кнопка «Отправить в сервис» шлёт файл на бэкенд, ждёт вердикт воркера и добавляет
его в отчёт. Адрес и учётные данные заданы в `config.py`:

```python
BASE_URL = "http://localhost:8000"
USERNAME = "demo"
PASSWORD = "demo"
```

Потоковый детектор гонит фонограмму через websocket `/audio/stream`: сигнал
приводится к 16 кГц моно int16, отправляется кусками по 0.5 с, а ответы воркера
(`current_score`) становятся кривой. Файловые детекторы идут другим путём —
через очередь RabbitMQ, и возвращают один вердикт на всю запись.

Важно: `streaming_worker.py` обрывает сессию на первом же вердикте `spoof`
(`status: terminated`). Поэтому на поддельной фонограмме кривая оборвётся в
точке срабатывания, а не пройдёт файл до конца. Для сквозного графика нужно
убрать досрочное завершение в потоковом воркере.

Учётная запись должна иметь роль SERVICE или ADMIN: `/audio/detect` отдаёт 403
обычному пользователю, а `POST /auth/register` создаёт именно USER — роль
меняется в базе вручную.

## Прослушивание

Кнопка «Слушать» проигрывает запись, по спектрограмме и графику оценок едет
отметка текущей позиции. Играет не файл, а уже декодированный сигнал, поэтому
работают все форматы, которые приложение открывает, включая дорожку из видео.

Звук идёт через QAudioSink из PySide6, отдельных пакетов не нужно. На голой
системе может не оказаться звукового сервера — тогда в журнал попадёт
«Не удалось воспроизвести», а анализ продолжит работать как обычно.

## Видео

Видеофайлы открываются наравне с аудио. Звуковая дорожка извлекается
копированием потока (`-acodec copy`), без перекодирования — чтобы не добавить
своих артефактов поверх исследуемых. Если дорожек несколько, приложение
спрашивает, какую исследовать, и записывает выбор в журнал.

Объектом исследования в отчёте остаётся исходный видеофайл: имя, размер и
SHA-256 берутся от него, а не от извлечённой дорожки.

## Пакетная обработка

Кнопка «Папка» прогоняет выбранный детектор по всем подходящим файлам каталога,
включая вложенные, и выгружает сводную таблицу CSV: длительность, число оценок,
максимум, средняя, участков выше порога, вердикт, ошибка.

Ошибка на одном файле не прерывает пакет — она попадает в отдельную колонку.
Разделитель `;` и кодировка utf-8-sig, чтобы Excel открывал без плясок.

Для больших пакетов нужна учётная запись с ролью SERVICE: у остальных лимит
10 запросов в минуту, и пакет упрётся в него почти сразу. Потоковые детекторы
для пакета не годятся по скорости, особенно PyAra — берите файловый режим.

## Форматы и сервис

Локально приложение открывает всё, что читает ffmpeg. Бэкенд SRW принимает
только wav, mp3, aac, flac и ogg, поэтому остальное (opus, wma, m4a, а также
дорожка, извлечённая из видео в контейнер mka) перед отправкой декодируется
в wav — с сохранением частоты и каналов, без пересжатия. Форматы из списка
уходят как есть.

Ограничение на размер файла задаётся переменной `MAX_FILE_SIZE_MB` для сервиса
`api` в docker-compose (по умолчанию 500). Пересборка образа не нужна,
достаточно перезапустить контейнер.

## Отчёт

Отчёт собирается не по последнему анализу, а по всему сеансу с момента загрузки
файла:

1. объект исследования — имя, размер, SHA-256, контейнер и кодек, частота, длительность;
2. таблица по всем запущенным детекторам — число оценок, максимум, участков выше порога, вердикт;
3. общий график: кривые всех моделей на одних осях плюс список участков;
4. классические признаки обработки;
5. журнал работы — время и событие по каждому шагу;
6. ограничения.

Журнал и накопленные результаты сбрасываются при загрузке новой фонограммы.

## Известные ограничения

- `find_repeats` даёт ложные срабатывания на тональных и стационарных сигналах;
  для речи порог 0.999 работает адекватно.
- Форматы со сжатием с потерями декодируются в PCM, то есть исследуется не
  исходный сигнал. Частота среза спектра на них показывает работу кодека, а не
  редактирование — отчёт это оговаривает отдельным абзацем.
- Для экспертизы оригинал файла нельзя подменять декодированным WAV: хеш и
  сведения о кодеке берутся из исходного файла.
- Оценка не является выводом о подлинности записи.
